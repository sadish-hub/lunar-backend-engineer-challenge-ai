**Goal:** Prove the live Lunar vendor harness can drive durable `POST /messages` on a running app + Postgres at `http://localhost:8088/messages`, under defaults and under non-default `--message-delay` / `--concurrency-level`, with HTTP **200** accepts and coherent `messages` + `channel_work` rows. **No apply correctness and no read APIs required.**

## Global constraints

- Path exactly `POST /messages` on port **8088**.
- Success status for accept is **200** (including duplicates); harness retries on non-2xx.
- Use real binary: `./rockets/darwin_arm64/rockets` or `./rockets/darwin_amd64/rockets` (not a hand-rolled curl loop as the primary gate).
- Vary **`--message-delay`** and **`--concurrency-level`** beyond defaults (defaults typically `500ms` / `1` per BRIEF).
- Assert **200** accept path + `messages` / `channel_work` durability — **not** applied `rockets` state or GET endpoints.
- YAGNI: no new features, no apply/read work, no coverage bar chase, no README polish beyond a short smoke note if needed.
- Process: plan → Driver OK → run smoke → review → Driver assess → commit (msg OK first).

## 1. Goals

1. Bring **app + Postgres** up locally so the service listens on **8088** with DB connectivity (e.g. `make up` then `make run`, or documented compose path).
2. Select the correct **darwin** harness binary under `rockets/` for the host arch.
3. Run harness **defaults** against `http://localhost:8088/messages` and confirm the run completes without protocol failure (accepts succeed as SPEC expects).
4. Run at least one **non-default** launch with both knobs stressed — e.g. tighter `--message-delay` and higher `--concurrency-level` — to exercise parallel POSTs and out-of-order delivery pressure on durable ingest.
5. Assert harness-facing accepts are **200** (no systemic 4xx/5xx that abort the run); optional sampling of app logs / status codes is enough if the harness itself reports success.
6. Assert DB after runs: rows exist in **`messages`**, and owed-work rows exist / remain coherent in **`channel_work`** for channels that received messages (dirty / claimable for later apply).
7. Record knobs used + outcome briefly (for checklist / later P4 re-run). Do **not** require `rockets` projection or read APIs.

## 3. Steps

### 3.1 Preconditions

1. Confirm P1 is on the branch under test (`POST /messages` durable + idempotent + `channel_work` upsert).
2. Confirm binaries exist: `rockets/darwin_arm64/rockets`, `rockets/darwin_amd64/rockets`.
3. Pick binary: `uname -m` → `arm64` ⇒ `darwin_arm64`; `x86_64` ⇒ `darwin_amd64`. Ensure executable bit if needed (`chmod +x`).

### 3.2 Bring up app + Postgres

```bash
make up          # Postgres via docker compose
make run         # Spring Boot on 8088
# optional: make smoke  # actuator health UP
```

Leave the app running for harness runs. Use a clean DB (or note prior rows) so post-run counts are interpretable.

### 3.3 Default harness run

```bash
./rockets/darwin_arm64/rockets launch "http://localhost:8088/messages"
# or ./rockets/darwin_amd64/rockets … on Intel Mac
# equivalent explicit defaults:
#   --message-delay=500ms --concurrency-level=1
```

**Expect:** harness completes; accepts are **200**; app stays up.

### 3.4 Non-default delay + concurrency run

Run again with **both** knobs varied beyond defaults (examples — adjust if harness rejects values; intent is faster delivery + parallel POSTs):

```bash
./rockets/darwin_arm64/rockets launch "http://localhost:8088/messages" \
  --message-delay=50ms \
  --concurrency-level=8
```

**Expect:** harness completes without protocol failure; ingest remains durable under load/reorder pressure. Optional third run (e.g. `100ms` / `4`) only if first stress run is flaky and Driver wants more evidence.

### 3.5 Assert HTTP 200 accept path

- Treat a clean harness completion against `/messages` as primary evidence of successful accepts (**200** per SPEC, including any retries that eventually succeed).
- If harness emits per-request status / error output, confirm no sustained 4xx/5xx that indicate contract break.
- Spot-check with `curl -i -X POST http://localhost:8088/messages …` only as a debug aid — not a substitute for the vendor binary.

### 3.6 Assert `messages` and `channel_work` rows

Against the live Postgres (compose credentials from `docker-compose` / `application.yml`):

```sql
SELECT COUNT(*) FROM messages;
SELECT COUNT(DISTINCT channel) FROM messages;
SELECT COUNT(*) FROM channel_work;
-- optional: sample that channels present in messages appear in channel_work
SELECT m.channel
FROM (SELECT DISTINCT channel FROM messages) m
LEFT JOIN channel_work c ON c.channel = m.channel
WHERE c.channel IS NULL;
```

**Expect:**

- `messages` count **> 0** after harness runs.
- `channel_work` has rows for channels that received messages (no “accepted but not claimable” gap for new inserts).
- Do **not** require `rockets` row counts or state correctness.
